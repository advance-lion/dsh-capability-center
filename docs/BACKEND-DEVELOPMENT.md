# 后端开发与动态验证门槛

## 范围与不变量

本阶段只建立独立的后端替换边界，不接管 `/api/capability-center`，不修改原 UI，不执行真实认证，也不修改正式 cache/runtime/credentials 文件。已有工作树改动不属于本阶段，不覆盖。版本完成以验收证据为准，不以接口数量或编译成功为准。

`src/core/runtime/backend-boundary.ts` 是后续静态/动态承载共用的核心源文件；它不依赖 Node、Cordis、DOM 或全局定时器。Vitest 直接导入这份源码。当前动态 pkg-6 是先前内存实验，不是这份源码的同源部署证据；必须完成构建与加载校验后才能替代它。

## 边界契约

- Backend 实例有唯一 id、contractVersion=1、动作白名单、只读 readiness check、execute、dispose。id 必须代表不可变版本；不是账号 id。
- readiness 仅表示后端可接请求，不表示任意外部账号认证有效。认证仍由具体 Recipe 的验证阶段负责。
- 激活前先校验契约，再执行只读 readiness check；失败保留原后端。
- 请求占用期间拒绝切换；切换检查期间拒绝新请求及第二次切换。
- 回滚是显式动作，重新检查前一版本；不承诺 Cordis Package 更新失败自动回滚。
- completed / waiting_user / failed 原样保留；未知动作或畸形结果必须失败。
- 操作入口捕获并冻结取消上下文，避免调用方修改 context.signal 后绕过取消。接受调用者的 AbortSignal；取消请求后即使后端不配合，也不释放实际在途占用，直到任务真实结束。提交点之前取消的候选，其晚到结果不得提交；提交点之后的取消不得谎报已经回滚。
- stop/dispose 先拒绝新请求，待真实任务结束后清理；清理失败记录脱敏错误码，并继续清理其他实例。dispose Promise 完成只代表所有清理尝试已结束；调用者仍须检查 cleanupErrors，不能把失败的清理宣称为已释放资源。
- 不会假装强杀不配合取消的后端。生产接入前必须由执行器提供真实超时/取消能力；永久悬挂任务会阻止安全切换或等待清理完成。

## 本阶段验收清单（先定义，再执行）

1. 空边界、无回滚目标、非法契约、未知动作都明确拒绝。
2. readiness 成功才能激活；失败/抛错不改变原后端。
3. 正在执行时不能切换；检查期间不能接入第二次切换或新请求。
4. 执行抛错释放计数；等待/业务失败不会变成成功。
5. 验证失败的回滚保留当前版本；成功回滚重新检查旧版。
6. 停止幂等；异步清理得到等待；一个清理失败不阻断其他清理。
7. 停止期间晚到的检查或执行结果不能成功，且自动清理，无额外手工 finishDisposal 补救。
8. 取消前不执行；取消中在实际结束前保持占用；取消的候选不得提交。
9. 候选外部对象的字段/方法被修改后，不改变已捕获版本的行为。
10. 丢弃的旧版本及时清理，只保留当前和前一回滚版本。

## 验证命令

```text
node node_modules/vitest/vitest.mjs run src/core/runtime/backend-boundary.test.ts
node node_modules/typescript/bin/tsc --noEmit
```

测试全部使用模拟后端和内存状态，不调用 CLI 登录或宿主重启。退出码和失败用例必须记录；`--passWithNoTests` 不作为验收方式。

## 分阶段部署规则

1. 本地隔离测试通过。
2. 从同一份源码生成纯 JavaScript Host Package；不能手工维护另一套业务逻辑。
3. 独立测试入口动态加载，检查源版本、失败路径、停止/重载和回滚。
4. 明确设计稳定路由调度层后，才安排一次受控接入；不得重复注册或抢占正式路由。
5. 只有底层加载器或不可迁移依赖确实需要时，说明理由并单独安排宿主重启。
